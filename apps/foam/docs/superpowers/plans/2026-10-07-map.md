# The Map (Foam Phase 4, Spec 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** The travel window picks the destination on a drawn map of Brno: each place is a small
button at its real position, the button under the map names the selection and makes the journey, and
the map shows the streets on foot and by taxi and the tram lines by tram.

**Architecture:** A Node script fetches the map's lines from OpenStreetMap into
`content/data/map.json`, in whole metres from an origin. Pure functions in `core/` project
positions, fit the map to its size, place the buttons and lay out the window; they are tested in
Node. `core/mapLayers.ts` turns the data into Pixi `GraphicsContext`s once (one-pixel `pixelLine`
strokes), and `screens/mapPicture.ts` renders a layer into an art-size `RenderTexture`, as
`PlacePicture` renders its shader. The travel window holds the picture, one 8 × 8 Tellurion `Button`
per place above it, and the destination button.

**Tech Stack:** TypeScript, Pixi.js 8.19 (`GraphicsContext`, `Graphics`, `RenderTexture`,
`renderer.render`, `renderer.extract`), Tellurion (`Modal`, `Panel`, `Container`, `Button`, `Text`,
`wrapText`), Vitest 4 (`unit` in Node, `browser` in Chromium), Node 24 scripts (`.mjs` importing
`.ts` through type stripping), Prettier 3, Overpass.

**Spec:** `apps/foam/docs/superpowers/specs/2026-10-07-map-design.md`

## Review Focus

- **The shared layer drawings outliving a closed window.** Every window builds a `MapPicture`, and
  closing the window destroys it. If that destroyed the shared contexts, the second window would
  draw an empty map. Pinned in Task 5: after a picture is destroyed, a new one draws the street.
- **The game's own places on the narrowest screen.** Real names wrap ("Brno hlavní nádraží"), so the
  destination button is 40 high there, and the centre's places lie a few pixels apart. Every window
  of the game's data must fit 146 × 262, and its place buttons must lie inside the map and not
  overlap. Pinned in Task 6.
- **A resize that changes the layout.** Turning a phone moves the window from stacked to side by
  side; the way, the selection and the focused control must survive the rebuild. Pinned in Task 6.
- **A destination without a position.** The selection works and the journey can be made, with no
  button and no dotted line for that place and one `console.warn`. Pinned in Task 6.
- **The side column on a short screen.** On a phone turned sideways (350 × 195) the column holds the
  row, a destination of 40 and "Back"; "Back" must not overlap the destination and must end level
  with the map. Pinned in Task 6.

### Task 1: The proof: one-pixel lines in an art-size texture

The spec's drawing rests on one fact not yet seen running: a path stroked with `pixelLine` and
rendered through a scaled container into a `RenderTexture` at resolution 1 lights one pixel per
step. This task proves it before anything is built on it.

**Files:**

**Interfaces:**

  `harness.game.app.renderer.extract.pixels({target})`) and `getColor(pixels, x, y)` (0xRRGGBB, or
  −1 for a pixel that is not opaque), written as in `tests/placePicture.browser.test.ts`. Task 5
  adds a second `describe` to this file and uses them.

- [ ] **Step 1: Write the proof**

`describe('a pixelLine stroke in an art-size texture', {timeout: 120_000}, …)`, booted with
`bootGame(960, 540)` and the `barPicture` mock. One drawing, made in `beforeAll` and read by every
test:

- A
  `pixi.RenderTexture.create({width: 40, height: 30, resolution: 1, scaleMode: 'nearest', antialias: false, dynamic: true})`.
- A `pixi.GraphicsContext` in units four times the pixels (as metres are to pixels on the map), one
  path of three subpaths, stroked once with `{color: palette.white, width: 1, pixelLine: true}`: the
  horizontal `(8, 20) → (148, 20)`; the diagonal `(8, 36) → (120, 92)`; the open polyline
  `(20, 108) → (60, 108) → (60, 80)`. A second context fills the ring
  `(128, 40) (152, 40) (152, 72) (128, 72)` with `palette.ground`.
- Both as `new pixi.Graphics(context)` in a container with `scale` `0.25` and `position`
  `(0.3, 0.6)`, rendered with
  `renderer.render({container, target, clear: true, clearColor: palette.black})`.

Tests (`white`, `ground`, `black` are the palette's values):

- `the horizontal line is one pixel thick`: for every x from 3 to 36, rows 3 to 7 hold exactly one
  `white` pixel.
- `the diagonal is one pixel thick in every column`: for every x from 3 to 29, with
  `y = Math.round(9 + ((x - 2) * 14) / 28)`, rows `y − 2` to `y + 2` hold exactly one `white` pixel.
- `subpaths are not joined and a path is not closed`: `(19, 7)` and `(20, 7)` (on a join from the
  horizontal's end to the diagonal's start) are `black`; `(10, 23)` and `(10, 24)` (on a closing
  segment of the polyline) are `black`.
- `a ring is filled inside its edge`: `(34, 13)` and `(35, 15)` are `ground`; `(31, 14)` is `black`.

Decisions the spec leaves to the plan:

- `toMapPixel` rounds with `Math.round`: `x = round(width / 2 + (point.x − centre.x) / mpp)`, and
  the same for `y`.
- `placeMapButtons` moves buttons in whole pixels. This is the algorithm; the tests pin its output:

```ts
// Boxes: each button {x: cx − 4, y: cy − 4, size 8}; the light, when given,
// {x: you.x − 4, y: you.y − 4, size 9}, fixed. For round in 1..20:
//   moved = false
//   for i < j over the boxes (the light last), in index order:
//     on each axis: a = the box whose centre is lower (on a tie, i),
//       gap = b.start − (a.start + a.size); need = BUTTON_GAP − gap
//     if need > 0 on both axes:
//       axis = the one with the smaller need (a tie takes x)
//       if neither box is the light: a moves −floor(need / 2), b moves +(need − floor(need / 2))
//       else the button moves the whole need, away from the light
//       moved = true
//   clamp every button to 0 ≤ x ≤ width − 8 and 0 ≤ y ≤ height − 8
//   if !moved: stop
```

- `getTravelLayout`: `sideBySide` when `screenWidth > screenHeight`. The stacked window is
  `min(WINDOW_WIDTH, screenWidth − 2 × MARGIN)` wide and `screenHeight − 2 × MARGIN` high, its
  `controlWidth` the window less `2 × WINDOW_PADDING_X`, `isNarrow` when
  `screenWidth < NARROW_WIDTH`. The side-by-side window is the screen less `2 × MARGIN` in both
  directions, `controlWidth` 120, `isNarrow` true. A `controlWidth` below 1 is 1.
- `getMapSize`: stacked, `controlWidth` wide and
  `window.height − 16 − 15 − 4 − 16 − 8 − 8 − destinationHeight − 8 − 16` high; side by side,
  `window.width − 24 − 8 − 120` wide and `window.height − 16 − 15 − 4` high. Each at least 1.

### Task 3: The map's data and the script that fetches it

**Files:**

- Create: `scripts/fetch-map-data.mjs`, `tests/fetchMapData.test.ts`,
  `source/game/content/data/map.json` (written by the script)
- Modify: `source/game/core/travel.ts` (the `MapData` type), `source/game/content/data/README.md`

**Interfaces:**

- Consumes: `getMapPoint`, `getMapPosition` (Task 2); `USER_AGENT`, `formatData` from
  `scripts/fill-travel-data.mjs` (importing it runs nothing: its run is behind
  `process.argv[1] === import.meta.filename`).
- Produces: `MapData` in `core/travel.ts`, as the spec's block. In the script:
  `export const MAP_MARGIN = 2000`, `export const SIMPLIFY_METRES = 5`, `export const LAYER_QUERIES`
  (the six selectors below), and
  `export async function fetchMapData(places, request): Promise<MapData>` with `places` the content
  of `places.json` and
  `request: (query: string) => Promise<Array<{id: number; geometry?: Array<{lat: number; lon: number}>}>>`,
  the `elements` of one Overpass answer.

Decisions the spec leaves to the plan:

- The selectors, each followed by the box `(south,west,north,east)` with every number `toFixed(5)`
  (in the table, `\|` stands for `|`):

  | Layer          | Selector                                                                            |
  | -------------- | ----------------------------------------------------------------------------------- |
  | `minorStreets` | `way[highway~"^(tertiary\|residential\|unclassified\|pedestrian\|living_street)$"]` |
  | `mainStreets`  | `way[highway~"^(motorway\|trunk\|primary\|secondary)$"]`                            |
  | `railway`      | `way[railway=rail][!service]`                                                       |
  | `rivers`       | `way[waterway=river][!tunnel]`                                                      |
  | `parks`        | `way[leisure=park]`                                                                 |
  | `tramLines`    | `way[railway=tram][!service]`                                                       |

  A query is `` `[out:json][timeout:90];${selector}${box};out geom;` ``, sent in the order of the
  table, one at a time. `south` and `west` come from
  `getMapPosition({x: box.left, y: box.bottom}, origin)`, `north` and `east` from
  `{x: box.right, y: box.top}`.

- A way: its points through `getMapPoint` (unrounded), simplified with Douglas–Peucker at
  `SIMPLIFY_METRES` keeping both ends (a segment of length 0 measures to its point), then rounded to
  whole metres, with a point equal to the one before it dropped. A line left with fewer than 2
  points is dropped. A park is kept only when its way is closed (first point equals last, compared
  in degrees) and its rounded ring still has at least 4 points.
- The run: `realRequest(query)` posts `{data: query}` to `https://overpass-api.de/api/interpreter`
  with `USER_AGENT`, reads the text, and throws
  `` `Overpass answered ${status}: ${text.slice(0, 80)}` `` when the status is not OK or the text
  does not start with `{`. The run reads `places.json`, awaits `fetchMapData`, writes `map.json`
  with `formatData`, and prints one line per layer (`minorStreets: 1234 lines`) and the file's size
  in KB. On an error it prints the message with `console.error`, sets `process.exitCode = 1` and
  writes nothing.

Decisions the spec leaves to the plan:

- `getMapLayers` keeps one result per data object in a module-level `WeakMap`. A line layer's
  context draws every line as one subpath (`moveTo` the first point, `lineTo` the rest) and strokes

  `poly(ring, true)` and fills once with `palette.ground`.
- `MapPicture` holds, besides `view` (a container with one `Sprite` of the texture), a scene that is
  never added to a screen: a layer container (one `pixi.Graphics(context)` per context of the
  current layer, rebuilt only when the layer changes; the old `Graphics` destroyed with no options)
  and one `pixi.Graphics` of marks in art pixels, cleared and drawn on every `draw`.

  `scale` is `1 / metresPerPixel` and its `position`
